A k3s Cluster on AWS, Managed Entirely from Git

k3s FluxCD Terraform SOPS Cloudflare Tunnel

I wanted to see how far I could push GitOps on a small cluster: servers created by Terraform, everything inside the cluster managed by Flux, and no manual kubectl apply after the first bootstrap. This is how it turned out: a k3s cluster on AWS with one master and one worker, where Git is the only way in.

Layer 1: The Servers (Terraform)

The cluster itself is plain Terraform. A t3.small master and t3.micro workers on Ubuntu 24.04, each configured by a user_data script that adds a 2 GB swapfile (these machines don't have much RAM to spare) and installs k3s.

I tried to leave nothing to copy by hand. Terraform generates the k3s join token and the SSH key, and workers join the master on their own at boot. Adding a node is a one-number change:

resource "aws_instance" "k3s_worker" {
  count      = var.worker_count
  depends_on = [aws_instance.k3s_master]
  # ... joins the master with the generated token
}

The security group is deliberately small: nodes can talk freely to each other, while SSH and the Kubernetes API are reachable only from my own IP. Only this part is AWS-specific, so moving the setup to another provider would mean rewriting the Terraform and nothing else.

Layer 2: Flux Takes Over

Once the cluster is up, a single command connects it to the repository and installs the Flux controllers:

flux bootstrap github \
  --owner=<user> \
  --repository=<repo> \
  --branch=main \
  --path=clusters/k3s-flux-lab \
  --personal

From that moment Git is the source of truth. The repo has three main areas: clusters/ is the entrypoint Flux watches, infrastructure/ holds everything that supports the cluster, and apps/ holds the workloads.

Infrastructure covers namespaces and base config, Reloader, Flux notifications, monitoring, logging (Vector and VictoriaLogs, which I wrote about in another note), the Cloudflare tunnel and RabbitMQ. RabbitMQ runs as a StatefulSet and its config and definitions live in Git too, so even the broker setup is reproducible. Apps are small things like a dashboard, a few IT tools, an EdgeHub agent and a node monitor. Every folder follows the same pattern: a kustomization.yaml plus plain manifests or a HelmRelease.

Secrets: SOPS and age

Putting passwords in Git sounds wrong until you encrypt them. I used SOPS with age: the private key is injected into the cluster once as a Kubernetes Secret, a .sops.yaml file maps the public key to every *.sops.yaml file, and Flux decrypts them on the fly:

spec:
  decryption:
    provider: sops
    secretRef:
      name: sops-age

The workflow is: write the Secret in plain text, run sops --encrypt --in-place, push. The risky step is forgetting the encryption, so a Git hook scans staged *.sops.yaml files and blocks the commit if the sops: metadata key is missing. It has already saved me from myself.

Networking: A Tunnel Instead of Open Ports

At first the AWS security group exposed ports 80 and 443 like any web server. Then I switched to Cloudflare Tunnels and closed them. The cloudflared daemon runs inside the cluster as a normal deployment, with its credentials encrypted by SOPS, and opens an outbound-only connection to Cloudflare. Nothing needs to reach the instances from the internet for HTTP traffic anymore.

The path of a request looks like this: Cloudflare terminates HTTPS, sends the request through the tunnel to cloudflared, which hands it to Traefik, which routes it to the right Service. All Services are now ClusterIP, so nothing is exposed on the host network. A new hostname is one command:

cloudflared tunnel route dns <tunnel-name> app.flowingbot.com

There's a bonus: with traffic going through Cloudflare, access rules live at the edge, and I can change who reaches what without touching the cluster. The one exception is non-HTTP traffic like RabbitMQ, which still uses NodePorts restricted to a short list of allowed IPs.

The Small Thing That Makes It Hands-Off

Here's a classic: you update a ConfigMap or a Secret and the Pods keep running with the old values. With GitOps you can't just restart them by hand, so I deployed Stakater Reloader through a HelmRelease. One annotation on a Deployment is enough:

metadata:
  annotations:
    reloader.stakater.com/auto: "true"

When Flux applies a change to the linked ConfigMap or Secret, Reloader triggers a rolling update. Commit, push, done.

The Takeaway

I think this is a really cool way to run a cluster. It's fairly cheap, because k3s is happy on small machines and the whole thing runs on a t3.small and a t3.micro. It's managed, because Flux keeps the cluster aligned with what's in the repo. And it's versioned: every change is a commit I can review, and revert if something goes wrong.

It also changed how I treat the cluster. Rebuilding it means terraform apply, a Flux bootstrap and re-injecting the age key (which of course never lives in the repo), so I can try things, break them and get back to a known state without stress. For a homelab, a small team or an edge test setup, it's a setup I'd happily recommend.
